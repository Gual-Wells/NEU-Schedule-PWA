# 组会生命周期：增量设计与发布边界

> v29 更新：五小时仍为认定上限；健身占用以真实确认结束时刻释放，未确认则跨日继续占用。组会统一进入每日 07:00 / 22:00 汇总，不再产生逐项推送。当前规则见 [事项协议](../protocol/AGENDA.md)。

> v31 更新：已取消独立的「安排组会」入口和表单。新增组会通过「事项」作为活动添加；下文旧组会参数继续适用于已有记录，查看、结束及取消操作保留。

## 业务语义
- 组会默认启用，不参与课程的“已翘/恢复”状态。
- 用户选取日期与开始时间。计划 3 小时实线；其后的 2 小时是弹性占用，显示虚线。最大时间认定窗口为 5 小时。
- 预定时间之后，界面根据绝对时间推定进行中，不需要“开始”按钮；该时间不是实际到场证明。
- 点击“结束组会”锁定终点。若晚于 5 小时才确认，认定终点只能取 5 小时，记录“超过上限后确认”，不能伪称此前实际结束。
- 超过 5 小时仍没有点击结束时进入 capped（待确认），无任何伪造的手动结束事件。
- 允许取消未来组会，禁止修改已完成记录；已完成记录不会被常规日程刷新自动重新打开。
- 与课程允许视觉并存，不改变默认翘课、放假调休和课程来源数据。与另一个组会的最长占用窗口不允许重叠。

## 数据权威与兼容
- 新建 D1 表 group_meetings；此前全部表和业务 JSON 不变。
- /state 与 /state/commit 仅增加 meeting-create/meeting-end/meeting-cancel 增量操作。
- 前端会议缓存只是离线与待同步缓存；云端 D1 为最终权威。
- 结束操作是单向条件更新，重试和其他设备的旧快照不能把它恢复为进行中。
- 全天真实分钟时间轴不改变；跨日组会按每天可见区间裁切，不在一个时间轴内画越界部分。
- 健身推荐与提醒扣除尚未结束组会的最多五小时占用，提前完成时释放剩余窗口。组会不能修改健身房物理开放范围。

## 发布顺序
1. 备份生产 D1 数据。
2. 在 D1 应用 0010_group_meetings.sql，确认 group_meetings 表和索引存在。
3. 部署支持新状态操作的 Worker，再部署包含新资源版本的 Pages。
4. 依次检查通行密钥登录、默认翘课、健身开始结束、组会安排、两种结束路径、前后台切换和跨设备恢复。
5. 不执行身份登记重置、不重新创建站点、不修改既有 Secret。

## 回归边界
应检查课程和健身旧功能测试全绿，组会生命周期、隔夜切分、单向结束、离线队列重放、推送任务去重及容量上限。
