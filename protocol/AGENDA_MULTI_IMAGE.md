# 一个导入任务、多张图片：附件协议 2

v30 增量。事项与完成状态继续使用业务协议 1；仅图片传输及运行器能力升级为附件协议 2。旧单图上传、历史导入与已经领取的识别任务继续兼容。

一批包含 1–8 张 PNG/JPEG/WebP 图片；每张压缩后最多 5 MiB、1600 万像素，每批合计最多 20 MiB，全局 50 MiB 存量限额保持。浏览器重编码剥离图片元数据。用户可以分次选图、预览、删除和排序；同字节图片自动忽略重复。浏览器 IndexedDB 保留压缩图片、顺序、说明、幂等 nonce 及服务端批次 ID，刷新或上传中断不丢草稿。本地草稿最多保留 72 小时，提交成功或主动取消即删除。服务端从创建批次开始保留图片最多 72 小时，原图到期后原文证据及来源编号仍可查看。

## 上传与识别

1. POST /imports/batches，登录会话及 Origin 校验，JSON 为 protocol:2、nonce、note、images。每张图片描述包含 id、digest（SHA-256 十六进制）、mime、byteLength；数组顺序固定为图 1、图 2……。服务端规范化完整清单连同说明计算摘要，同 nonce 不同内容返回 409；在事务内预留整批容量。
2. 初始业务 status 为 queued，uploadState 为 draft。POST /imports/{id}/images/{imageId} 上传单张原始图片字节。服务器核验大小、格式、像素和摘要，与清单一致后在同一事务中写入分片及 receivedAt。重复上传不重复写入，取消与上传竞争由 SQL guard 拒绝，不能复活已取消图片。
3. GET /imports/{id} 返回清单及每张 receivedAt。浏览器重试只补传 receivedAt 为空的图片。全部到齐后 POST /imports/{id}/submit 将 uploadState 原子改为 ready；缺图返回 409。重复提交不会重复进入模型任务。
4. 未 ready 的批次绝不能领取。新运行器使用 POST /runner/claim，JSON 带 protocol:2；旧运行器未声明能力，只能领取旧单图任务。新 job 携带 protocol:2 和按 position 排序的 images，各自包含 id、mime、digest、byteLength、position、path。
5. 运行器按顺序读取所有 /runner/image/{id}/{imageId}，每张验证摘要，再通过一次模型调用联合分析。所有图片共享同一 claim、五分钟租约及领取代次。图片路径只能属于当前导入任务。模型不具备业务写权限，租约失效不自动重新推理。
6. 候选 sourceImages 是从 1 开始的非空、去重整数数组，必须引用本批次图片。跨图补齐同一事项的内容、时间、地点，重复通知合并；无法判明同一事项、日期矛盾或缺少可靠时间时，置空相关日期并在 question 标明依据，不能按图片顺序覆盖。v32 起每次仅生成一项；用户核对只读结果后整体应用，修改通过同一申请文字反馈重新生成，详见 [单项审核](AGENDA_SINGLE_REVIEW.md)。

上传开始后清单不可变。需要更换、增删或重排图片时，先取消当前上传，再提交新的批次；避免识别结果引用的图号变化。已经提交识别的批次不允许追加图片；现有事项的任意补图重识别属于后续单独功能。

## 来源与兼容

审核界面展示图号及每张原图入口。确认入表时从保留的原始候选写入 sourceImportId、sourceImages，客户端不能伪造来源。GET /imports/{id}/source/{position} 仅登录用户可用，按固定顺序取图；所有业务图片和接口 no-store，Service Worker 不缓存。

旧单图 POST /imports 继续接受上传；新上传同样使用单项提取。旧输出没有 sourceImages 时仅对旧单图任务补为 [1]；多图结果缺少来源或越界一律拒绝。历史已应用事项没有来源数组时按原单图处理。原有课程、默认翘课、时间窗、健身占用和早晚汇总语义不变。

发布顺序：备份并验证恢复 → 应用 0012 → 部署兼容新旧运行器的 Worker → 安全更新本机运行器及 schema → 发布 PWA v30 → 核对凭据、旧单图和空队列运行。迁移仅新增字段和附件表；回退保留新数据，旧运行器不能领取多图任务。多图会增加现有 ChatGPT 图片处理配额及网络用量，不开通新付费服务。
